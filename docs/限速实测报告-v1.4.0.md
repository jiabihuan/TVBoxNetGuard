# v1.4.0 断网问题：定位与实测验证报告

## 一、用户现象

> "只要一开引擎，盒子就全部断网了，别的软件也连不上了"

## 二、根因：上行限速把 TCP 的 ACK 一起掐了

**下载数据必须靠上行 ACK 确认。** 早期版本对所有出站包一视同仁地限速，
于是出现这个连锁反应：

```
给 uid 限速 → 该 uid 的纯 ACK 小包（40~60 字节）也计入配额
           → 配额被数据大包吃满，ACK 发不出去
           → 对端收不到确认，停止下发数据
           → 表现为"断网"
```

root 流量闸（uid 0 上行限 128 KB/s = **87 pps**）踩得最狠：
**系统服务、DNS、内核发出的 TCP ACK 全是 uid 0**，87 pps 的配额
在正常下载时几毫秒就被吃光，于是**整台盒子连不上网**——
这就解释了"别的软件也连不上了"。

`Prefs.kt` 里那句注释「系统自身以 root 发出的上行极少，不受影响」
是错误假设，正是 bug 的温床。

## 三、实测环境

两台 netns 之间架 veth，用**不同 uid 的进程**模拟不同 App（对应 Android 的 App uid）：

| uid | 扮演 | 端口 |
| --- | --- | --- |
| 10001 | 剧迷TV（PCDN，被限速目标） | udp 5001 / tcp 5101 / 5201 |
| 10002 | 普通应用（不能被误伤） | udp 5002 / tcp 5102 / 5202 |
| 0 | root / 系统服务（DNS、内核 ACK） | udp 5003 / tcp 5103 / 5203 |

脚本：`labtest/flow.py`（流量发生器）、`labtest/lab.py`（场景驱动）、
`labtest/compare.py`（方案横向对比）。所有数值均为**服务端/客户端实测有效吞吐**。

> 注：veth 回环带宽极高（GB/s 级），绝对值不代表真实网络，
> 结论看的是**同一环境下的横向对比**。

## 四、实测结果

### 4.1 核心验证：限得住 + 不断网

目标：把剧迷TV 的上行压到 200 KB/s。

| 场景 | 剧迷TV 上行 | 普通应用上行 | root 上行 | 剧迷TV 下行 | 普通应用下行 | root 下行 |
| --- | --- | --- | --- | --- | --- | --- |
| ① 基线（无规则） | 78 MB/s | 78 MB/s | 89 MB/s | 5.4 GB/s | 6.1 GB/s | 4.6 GB/s |
| ② **限速 200 KB/s** | **186 KB/s** ✅ | 226 MB/s ✅ | 170 MB/s ✅ | 4.95 GB/s ✅ | 5.5 GB/s ✅ | 5.4 GB/s ✅ |
| ③ **禁 UDP** | **0** ✅ | 192 MB/s ✅ | 188 MB/s ✅ | 4.84 GB/s ✅ | 5.1 GB/s ✅ | 5.5 GB/s ✅ |

- **限得住**：186 KB/s vs 目标 200 KB/s（按 1500 字节满包折算，略偏严属预期）
- **不误伤**：普通应用与 root 的上下行都在基线水平，有的还因为对手让出带宽而更高
- **禁 UDP 精准**：UDP 归零，TCP 下载 4.84 GB/s 完全正常 —— PCDN 掐死、视频照看

### 4.2 断网 bug 的复现与修复对比

| 场景 | root 上行 | **root 下行** | 结论 |
| --- | --- | --- | --- |
| ④ 旧配置：root 闸 128 KB/s、**无**小包豁免 | 118 KB/s | **308 MB/s**（基线 4.6 GB/s，**-93%**） | ❌ 复现"整机断网" |
| ⑤ 新配置：root 闸 512 KB/s、**有**小包豁免 | 481 KB/s | **5.06 GB/s**（回到基线水平） | ✅ 恢复正常 |

剧迷TV 自己被限速时也一样：旧配置下它的下行从 5.4 GB/s 掉到 154 MB/s（-97%，
等于"这个软件也连不上网了"），新配置下恢复 4.97 GB/s。

### 4.3 方案选型：为什么最终继续用 `-m limit`

曾怀疑 `-m limit` 令牌桶不恢复（早先测出"只放行 27 个包"，一度判定它失效），
于是试验了无状态比例丢弃 `-m statistic --mode nth`。修正测量方法后重测：

| 方案（目标 200 KB/s） | 实测 | 判定 |
| --- | --- | --- |
| `iptables -m limit 136/s` | **172 KB/s** | ✅ 精确，令牌恢复正常 |
| `iptables -m statistic nth every 15` | 38 MB/s | ❌ 太松 |
| `tc + htb 1600kbit` | **190 KB/s** | ✅ 最精确 |

`nth` 是比例丢弃，实际限速值 = 应用原始速率 ÷ every，而"应用原始速率"
随环境剧烈变化（同一 every=15，5 MB/s 宽带上是 333 KB/s，高速链路是 38 MB/s），
完全不可控，**已弃用**。早先的"limit 失效"是测试脚本自身的 bug
（UDP 客户端因 ICMP 崩溃 + 统计时间窗错误）造成的假象。

## 五、v1.4.0 的改动

| 改动 | 说明 |
| --- | --- |
| **小包豁免（核心修复）** | iptables 路径限速规则前插 `-m length --length 0:200 -j ACCEPT`；tc 路径只对 >400 字节的包 `CLASSIFY`；VPN 引擎中 ≤128 字节的包不扣令牌桶。ACK / DNS 一律放行 |
| **root 流量闸默认关闭** | 它最容易踩到 ACK 饿死；现在默认关闭，需要时在设置页手动开（打开后也已豁免小包） |
| **闸值放宽** | 128 KB/s → 512 KB/s |
| **tc 安全阀** | 校验 htb 的 default class 是否真的建成，建不起来就回滚 qdisc 并回退 iptables，避免"未分类流量被丢弃 = 整机断网" |
| 版本 | 1.3.0 → **1.4.0**（versionCode 5） |

`blocked`（彻底断网）与「上行 0」不受小包豁免影响，照旧全丢 —— 该封的还是封得住。
